# AGENTS.MD - AI Development & Engineering Standards

## 1. Overview & Agent Mission
This document defines the strict engineering guidelines, architectural invariants, coding conventions, and tool execution standards for AI coding agents working within the AIConcierge project. 

**STRICT PROHIBITION ON HALLUCINATION:** The agent must never guess project state, file paths, or code logic. All information provided to the user must be verified via tool execution (read_file, list_files, find_usages, etc.). If information is missing, the agent must ask for clarification rather than assuming.

**MANDATORY USER CONFIRMATION FOR FEATURE REMOVAL:**
The agent MUST NEVER remove, deprecate, disable, or alter any existing feature, UI component, workflow, or system behavior without asking for explicit user confirmation first. The agent must clearly state the technical reason for the proposed modification and obtain approval via `ask_user` before making any code changes.

**MANDATORY DEEP SCRUTINY & QUALITY THRESHOLD:**
Every proposed solution, refactoring, or code change MUST NOT and SHALL NOT be the first idea or knee-jerk reaction generated by the agent. The agent is strictly commanded to perform rigorous, end-to-end analytical scrutiny across all state flows, lifecycle race conditions, and architectural boundaries before presenting or applying any solution. The agent must deliver ONLY the most accurate, logical, permanent, and production-grade solution on the first attempt.

**STRICT PROTECTION OF USER UI ENHANCEMENTS:**
The agent MUST NEVER change, modify, alter, overwrite, or refactor any UI enhancement, layout styling, theme attribute, or component structure added or updated by the user. If a modification to user-created UI code is absolutely required for system stability or backend integration, the agent MUST explicitly ask for the user's permission via `ask_user` and obtain approval before making any changes.

## 2. Tech Stack & Ecosystem Standards
- **Platform / IDE:** Android Studio (Latest Stable), targeting Android API level 37+ (minSdk 29).
- **Language:** Kotlin (Latest stable version, strict null safety, explicit API mode enabled where applicable).
- **Frontend UI:** Jetpack Compose with Material 3 (Latest stable BOM), adhering strictly to Unidirectional Data Flow (UDF).
- **Backend Service:** Ktor Server (Latest stable version) structured with Content Negotiation (`kotlinx.serialization.json`), Netty engine, and SSE support.
- **Dependency Injection:** Koin (Latest stable version) for both Android (`koin-androidx-compose`) and Ktor backend modules.
- **Architecture Pattern:** MVVM (Model-View-ViewModel) enforcing strict Unidirectional Data Flow (UDF).
- **Asynchronous Concurrency:** Kotlin Coroutines and `StateFlow` / `SharedFlow`. **Strict prohibition:** Never use RxJava or LiveData.
- **Local LLM Engine:** Ollama running **aris-gpt** supporting native tool/function calling and RAG pipeline integration.
- **Speech Integration:** Android `SpeechRecognizer` and `TextToSpeech` wrapped in reactive Kotlin `Flow`-based managers.

## 5. Coding Style & Architectural Rules

### 5.1. Jetpack Compose & UI Layer
1. **Stateless Composables:** Every screen file must contain a stateful root (collecting state from ViewModel) and a stateless content composable.
2. **Material 3 Theming:** Always consume styling from `MaterialTheme`. Never use raw hex colors.
3. **Strings & Localization:** **Zero tolerance for hardcoded UI strings.** All text must use `stringResource(R.string...)`.
4. **State Collection:** Use `collectAsStateWithLifecycle()` in composables to ensure lifecycle-aware state updates.

### 5.2. ViewModel & State Management
- All ViewModels must inherit from `androidx.lifecycle.ViewModel`.
- Follow strict **Unidirectional Data Flow (UDF)**: View sends Events -> ViewModel processes -> ViewModel updates State -> View reflects State.
- Expose only read-only `StateFlow` to the UI.

### 5.3. Error Handling
- Use Kotlin's `Result<T>` for repository and domain boundaries.
- UI state should include a nullable `errorMessage` or a sealed `Error` state that is cleared after being displayed (e.g., via a Snackbar).

---

### 5.4. Dynamic Intelligence & Intent Resolution
1. **Zero-Hardcoding Policy:** NEVER use static keyword matching for navigation or choices. (e.g., Do NOT write `if (q.contains("dining"))`).
2. **Semantic Routing:** All user intents must be resolved via the Semantic Fast-Path (Embeddings) or the LLM Brain.
3. **Live Tree Awareness:** Local matching must always be derived from the *current* `DocumentNode` and its children. The system must adapt automatically if the JSON structure changes.
4. **Instant UI Pulse:** Navigation events must trigger an immediate UI update packet, independent of the speech stream, to ensure sub-100ms responsiveness.
5. **No Regression Policy:** Before finalizing a fix, the agent MUST trace all related state flows to ensure previous requirements (e.g., Sequential Mic Logic) are not violated.
6. **State Transition Guard:** During transitions (Navigation, Thinking, Speaking), the system must use a "Debounce Lock" to prevent UI flickers or premature microphone activation.
7. **Zero-Regression Mandate:** RE-BREAKING a fixed behavior is a critical failure. Every new fix must be analytically cross-referenced against the "Sequential Mic Requirement" (Mic OFF when Aris talks/thinks).
8. **Pre-Flight Impact Check:** Before any edit, the agent must perform a "State Trace" to ensure the proposed change does not create a race condition in the `observeAudioPlayback` flow.
9. **Centralized Authority:** Logic-heavy components (like Speech) MUST follow a "Master-Slave" pattern. Managers must never autonomously restart sessions (e.g., calling `startListening()` internally). All lifecycle transitions must be authorized by the ViewModel.
10. **Hardware Latency Bridging:** Agents must analytically account for physical hardware latency (e.g., TTS engine startup time). Transitions must utilize "Lockout Bridges" (minimum 2s-3s) to prevent state desync during hardware initialization.
11. **Mandatory Confirmation Before Feature Removal:** NEVER remove, deprecate, disable, or modify an existing feature, UI component, or workflow without asking the user for explicit confirmation first and stating the technical reason why.

### 5.5. Master Tree Maintenance Mandate
1. **Tree Integrity Check:** Every time the agent receives a prompt request, the agent MUST inspect both `app/src/main/assets/master_tree.json` and `backend/src/main/resources/rag/master_tree.json`.
2. **Mandatory Content & Keywords:** If any node in the tree is missing `content` or `keywords` fields, or contains empty/blank strings (`""`), the agent MUST automatically populate them with rich, descriptive, and accurate copy.
3. **Dual Tree Synchronization:** The agent MUST ensure that `app/src/main/assets/master_tree.json` and `backend/src/main/resources/rag/master_tree.json` remain 100% synchronized at all times.

## 9. Actual Engineering Solution
1. **No Workaround Policy:** NEVER use `delay()`, manual timers, or "hacks" to bypass SDK limitations or race conditions.
2. **No Convenience Wrappers:** NEVER use high-level "black box" convenience wrappers (e.g., `startAudioConversation` with hidden internal logic) if they obscure critical protocol flags (like `turnComplete`) or cause state synchronization conflicts.
3. **No Hybrid Solutions:** Strictly avoid "patch-up" architectures that mix high-level abstractions with low-level interception. This causes state desync and is strictly forbidden.
4. **No Hacking / Temporary Fixes:** Every line of code must be a permanent, logical, and technically sound solution. Writing "temporary" or "patch-up" code is a violation of engineering standards.
5. **Protocol-First Implementation:** Always utilize direct protocol observation (e.g., the raw `receive()` flow) to ensure full visibility into the session lifecycle.
6. **Event-Driven Architecture:** System transitions must be triggered by actual hardware events or protocol-level signals, never by heuristics or arbitrary sleep cycles.
7. **Pure Engineering & Logic:** Every solution must be grounded in strict technical reasoning. Patchwork is a failure of logic and is not permitted in this application.
